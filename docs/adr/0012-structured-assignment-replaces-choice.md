# Ingestion assigns threads with one structured call per chunk, not one Choice per message

Amends ADR-0006 (scope of the Decision tier) and ADR-0009 (PII in the wiki).

**Context**: ADR-0006 put thread assignment on the Decision Model: one *Choice* question per message over `{each active thread, new-thread, chatter}`. In production that decided each message in isolation — the model never saw the rest of the batch, so a topic split across three messages could land in three places; `new-thread` grouping was a "consecutive messages" heuristic, not a judgement; a new thread's title needed a separate Worker call; and neither call was told who sent a message or when. Separately, the pages themselves were wrong for their readers: Timeline lines showed the sender's jid, `participants:` was a wikilink to a phone number, and the channel index linked threads by absolute Lapis URL instead of a wikilink.

**Decision**:

1. **Assignment is one structured Worker call per chunk of messages.** The model sees the channel's active *and* stale threads (slug, title, description, recent lines) plus every message in the chunk (id, send time, sender name **and** jid, reply target, text), and returns JSON: one thread per message — an existing slug, a `new-N` it declares with a title and description, or `chatter`. Chunks are cut on an estimated token budget (`INGEST_MAX_PROMPT_TOKENS`, `INGEST_MAX_MESSAGES_PER_CALL`); threads minted by one chunk are shown to the next as existing threads, so a topic spanning a chunk boundary still lands in one thread. Answers are validated against the ids and slugs actually in the prompt, and a bad answer is re-asked with the specific problem stated; whatever survives that is dropped as chatter with a logs-channel notice, never left to block the batch.
2. **Replies never reach the model.** A `replied_to_id` pointing at a message already on a thread page routes straight there; one pointing at a message in the same batch follows that message wherever it lands. Both are shown to the model as context, never as something to assign.
3. **Summary, Items and title are one structured call per touched thread**, replacing three (`name-thread`, `summarise-thread`, `extract-items`). Items come back as typed objects and are rendered into the Wiki Format grammar in code, so a malformed item line is now impossible rather than filtered out after the fact; an item whose `src_ids` don't match a real message is dropped.
4. **The ingestion prompts are code constants, not skills.** Skills (`skills/*/SKILL.md`, `meta/skills/`) stay for the Chat Agent and the benchmark harness, but ingestion is the core of the product and runs on every batch: a short exact prompt costs fewer tokens than a loaded skill bundle, and this behaviour should not change because someone edited a wiki page.
5. **No PII stripping anywhere in ingestion.** The wiki is internal to the club. Sender jids go into the prompt (they disambiguate two people with the same display name), and a phone number a member actually typed stays in the summary. Pages still render *people* by name — `[[Member]]` when the sender is linked in the registry, their WhatsApp display name otherwise, and the jid only when gowa gave no name at all. `lint_text` no longer reports phone/email-shaped strings; `contains_pii`/`redact_pii` remain for any caller that wants an opt-in scrub.
6. **The channel index links threads with wikilinks** (`- [[channels/<dir>/<slug>|Title]] — last <date>`), as Wiki Format always specified — rename-safe and resolvable in both Obsidian and Lapis, unlike the absolute Lapis URLs it was writing. `sunday_stale_nudge` still uses URLs: it posts to WhatsApp, where a wikilink means nothing.

**Consequences**: the Decision Model (Jev) is now used only by the Chat Agent (thread identification, approval interpretation), so `JEV_API_KEY` is optional for ingestion. Model calls per batch go from `one Choice per message + three Worker calls per touched thread` to `ceil(messages / chunk) + one per touched thread`, with a bigger prompt each. Assignment quality now depends on one cheap model reading a whole batch, so `INGEST_MODEL_NAME` can point the two ingestion calls at a stronger model than the Worker without changing anything else. The Worker model must handle a JSON-schema-in-prompt contract (`PromptedOutput`) — no tool-calling support needed, but a model that cannot produce valid JSON at all is no longer usable for ingestion.

**Alternatives rejected**: keeping the Choice path behind a config flag (two ingestion paths to test and reason about, for a decision already made); one call per batch returning assignment *and* every thread's summary and items (a much larger, more fragile output schema, and it re-summarises threads no message touched).
